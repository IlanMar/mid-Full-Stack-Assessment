# Руководство по Transaction Monitor

## Что было создано

Приложение имитирует финансовые транзакции и отображает их в реальном времени. API на ASP.NET Core хранит в памяти последние 200 принятых транзакций. Фронтенд на React и TypeScript состоит из двух экранов.

| Экран | Назначение |
| --- | --- |
| `/add` | Создаёт одну транзакцию или пакет из 100 транзакций. Пакет отправляет до десяти запросов одновременно и показывает количество успешных запросов. |
| `/monitor` | Показывает последние транзакции, состояние подключения и фильтр **Errors only**. Новые строки ненадолго подсвечиваются, если не включено уменьшение движения. |

## Как это работает

1. Симулятор отправляет транзакцию в формате JSON на `POST /api/transactions`. API проверяет входные данные перед изменением ленты.
2. Хранилище в памяти присваивает каждой принятой транзакции порядковый номер. Одна блокировка защищает проверку дубликатов, присвоение номера, добавление и удаление старых записей. Эндпоинт снимка копирует очередь под той же блокировкой, чтобы читатели получали согласованное представление.
3. После освобождения блокировки API рассылает подключённым клиентам событие `TransactionAdded` через хаб SignalR по адресу `/hubs/transactions`. События могут приходить не по порядку, поэтому фронтенд сортирует их по присвоенному сервером порядковому номеру.
4. Монитор подключается к хабу до отправки запроса `GET /api/transactions`. Он буферизует события, приходящие во время запроса, и объединяет их со снимком по идентификатору транзакции. После восстановления подключения он загружает новый снимок и заменяет им прежнее представление. В ленте сохраняется не более 200 строк.

API использует тип `decimal` для сумм. Он принимает статусы `Pending`, `Completed` и `Failed`, трёхбуквенный код валюты в верхнем регистре, непустой UUID и временную метку UTC, оканчивающуюся на `Z` или `+00:00`. Статус фиксируется при принятии транзакции. Порядковый номер хранится отдельно от самой транзакции. И снимок, и событие в реальном времени используют оболочку `{ sequence, transaction }`.

Проверка дубликатов применяется к идентификаторам, которые ещё находятся в очереди. Старые записи удаляются, а перезапуск API очищает всю историю. Монитор после отключения может восстановить только историю, которая ещё хранится на сервере.

| Где искать | Назначение |
| --- | --- |
| [Program.cs](backend/Monitor.Api/Program.cs) | HTTP-эндпоинты и настройка SignalR |
| [TransactionStore.cs](backend/Monitor.Api/TransactionStore.cs) | История в памяти, порядок записей и защита от дубликатов |
| [main.tsx](frontend/src/main.tsx) | Экраны симулятора и монитора |
| [useTransactionFeed.ts](frontend/src/useTransactionFeed.ts) | Подключение, загрузка снимка и восстановление подключения |
| [feed.ts](frontend/src/feed.ts) | Объединение, удаление дубликатов, сортировка и хранение записей на клиенте |

## Локальный запуск

Установите .NET 8 SDK и Node.js версии 22.12 или новее. Выполняйте эти команды из корня репозитория.

В первом терминале запустите API.

```sh
dotnet run --project backend/Monitor.Api --urls http://127.0.0.1:5080
```

Во втором терминале запустите фронтенд.

```sh
npm --prefix frontend ci
npm --prefix frontend run dev
```

Откройте [симулятор](http://localhost:5173/add) и [монитор](http://localhost:5173/monitor). Дождитесь появления статуса **Live** на мониторе. Vite перенаправляет запросы API и WebSocket на порт 5080, поэтому оба терминала должны оставаться открытыми.

Если монитор остаётся в состоянии **Connecting**, проверьте, что API отвечает на [эндпоинте проверки состояния](http://127.0.0.1:5080/health) и что Vite прослушивает порт 5173.

## Тестирование

### Автоматические проверки

Выполните команды из корня репозитория после установки зависимостей фронтенда.

```sh
dotnet test backend/Monitor.Tests
npm --prefix frontend test
npm --prefix frontend run build
```

| Проверка | Что проверяется |
| --- | --- |
| Тесты хранилища бэкенда | Дублирующиеся идентификаторы, удаление старых записей и параллельное чтение и запись |
| Тесты API бэкенда | Валидация, ответы на дубликаты и доставка принятых транзакций двум клиентам WebSocket |
| Тесты фронтенда | Объединение снимков и событий, доставка не по порядку и ограничение в 200 записей |
| Сборка фронтенда | Проверки TypeScript и создание сборки для продакшена |

### Проверка в браузере

1. Откройте симулятор и две вкладки монитора. При свежем запуске API оба монитора должны показывать пустую ленту и статус **Live**.
2. Нажмите **Send one**, затем **Send 100**. Симулятор должен сообщить, что неудачных запросов нет, а оба монитора должны показать одни и те же 101 транзакцию в одинаковом порядке.
3. Включите **Errors only**. Все видимые строки должны иметь статус `Failed`. Снимите фильтр и убедитесь, что остальные строки вернулись.
4. Перезагрузите один монитор. Он должен показать ту же ленту из снимка. Остановите и перезапустите API, не закрывая монитор, чтобы проверить автоматическое восстановление подключения. При перезапуске история очищается, а новые отправленные транзакции появляются после возвращения монитора в состояние **Live**.
5. Отправьте три пакета по 100 транзакций при выключенном фильтре. Монитор должен показывать только 200 записей и продолжать реагировать на фильтр.

### Прямое обращение к API

В PowerShell отправьте корректную транзакцию работающему API.

```powershell
$url = 'http://127.0.0.1:5080/api/transactions'
$body = @{
    transactionId = [guid]::NewGuid().ToString()
    amount = 12.50
    currency = 'USD'
    status = 'Completed'
    timestamp = [DateTimeOffset]::UtcNow.ToString('o')
} | ConvertTo-Json

(Invoke-WebRequest -Uri $url -Method Post -ContentType 'application/json' -Body $body).StatusCode
Invoke-RestMethod -Uri $url
```

POST должен вернуть `201`. Новая запись должна появиться первой в снимке и на всех подключённых мониторах. Отправьте то же тело запроса повторно, чтобы проверить ответ `409 Conflict`, затем попробуйте отправить `'{}'`, чтобы проверить ответ `400 Bad Request`. Ни один из отклонённых запросов не добавляет запись.

## Запуск упакованного приложения

Dockerfile собирает фронтенд и API на отдельных этапах. Итоговый образ обслуживает оба компонента на порту 8080.

```sh
docker build -t transaction-monitor:local .
docker run --rm -p 8080:8080 transaction-monitor:local
```

Откройте [монитор упакованного приложения](http://localhost:8080/monitor) и [симулятор](http://localhost:8080/add). Чтобы попробовать манифесты Kubernetes, сначала загрузите образ в локальный кластер или измените конфигурацию развёртывания, чтобы использовать образ из вашего реестра.

```sh
kubectl apply -f k8s
kubectl port-forward service/transaction-monitor 8080:8080
```

Развёртывание использует одну реплику и проверяет готовность по адресу `/health`. При использовании нескольких реплик каждая из них будет иметь собственную очередь и собственный набор подключённых клиентов. Для масштабирования потребуются общее хранилище истории, порядковых номеров и данных для проверки дубликатов, а также SignalR backplane для доставки событий в реальном времени между репликами.
